# AI 股票分析面板项目文档

## 1. 项目目标

### 1.1 背景
- 本项目用于完成一个 48 小时内可交付的全栈面试题。
- 目标是构建一个 A 股优先的 AI 股票分析面板。
- 用户输入股票代码后，系统拉取行情数据、调用大模型生成结构化分析结果，并将分析记录存入 Supabase。

### 1.2 项目目标
- 在网页端提供简洁清晰的股票分析体验。
- 让 LLM 输出严格结构化 JSON，而不是自然语言散文。
- 保证分析结果可追溯、可查询、可展示历史记录。
- 最终支持 Render 部署并提供公开访问 URL。

### 1.3 首版范围
- 支持 A 股 6 位股票代码。
- 支持行情概览、K 线图、AI 分析结果、历史记录查询。
- 不做用户登录页，但数据库预留 `user_id`。
- 不支持港股、美股、指数、实时分时行情。

## 2. 技术选型

### 2.1 前端
- `React + TypeScript + Vite`
- `Tailwind CSS + shadcn/ui`
- `ECharts`
- `TanStack Query`

选择理由：
- `Vite` 适合从零快速交付，开发和构建速度快。
- `React + TypeScript` 组件生态成熟，适合中小型面板类应用。
- `Tailwind + shadcn/ui` 可以在短时间内做出统一、可维护的 UI。
- `ECharts` 对 K 线、均线、成交量等金融图表支持成熟。
- `TanStack Query` 能简化接口请求、缓存、加载态和错误态管理。

### 2.2 后端
- `FastAPI`
- `Pydantic v2`
- `AkShare`
- `SiliconFlow OpenAI-compatible API / DeepSeek`
- `supabase-py`

选择理由：
- `FastAPI` 适合快速构建类型明确的 API 服务。
- `Pydantic v2` 非常适合做请求校验、响应建模、LLM 结构化输出校验。
- `AkShare` 对 A 股数据获取更顺手，减少自行拼第三方接口的工作量。
- `SiliconFlow` 适合用 OpenAI-compatible 接口快速接入结构化输出。
- `Supabase` 可以直接提供 Postgres 存储能力，部署和管理成本低。

### 2.3 存储与部署
- 数据库：`Supabase Postgres`
- 前端部署：`Render Static Site`
- 后端部署：`Render Web Service`

选择理由：
- `Supabase` 足够支撑首版分析记录存储，且后续可平滑接入 Auth。
- `Render` 对静态站点和 Python Web Service 都有成熟托管方式。

## 3. 系统架构

### 3.1 架构概览
- 前端负责用户输入、结果展示、图表渲染、历史记录浏览。
- 后端负责股票数据拉取、均线计算、Prompt 构造、DeepSeek 调用、JSON 校验、Supabase 入库。
- 所有数据库读写均由后端处理，前端不直连 Supabase。

### 3.2 核心模块

前端模块：
- 页面路由：分析页、历史记录页
- 数据请求层：统一 API 调用和错误处理
- 图表组件：K 线、均线、成交量
- 分析结果组件：情绪、风险、摘要、驱动因素、风险因素

后端模块：
- 路由层：健康检查、股票概览、分析、历史记录
- 数据服务层：AkShare 数据获取与清洗
- AI 服务层：Prompt 构造、DeepSeek 调用、Pydantic 校验
- 存储服务层：Supabase 查询和写入

## 4. 开发流程

### 4.1 开发原则
- 先跑通最小闭环，再逐步补历史页、异常处理、部署和文档。
- 先保证数据和接口稳定，再完善 UI 细节。
- 所有对外 API 先定结构，再写实现。
- 所有 AI 输出必须经过 schema 校验后才能返回前端。
- `POST /api/analyses` 只允许前端提交 `symbol`，后端必须自行拉取行情快照后再分析和入库。

### 4.2 推荐开发顺序

#### 阶段 1：项目初始化
- 初始化前端 Vite 项目和基础目录结构。
- 初始化 FastAPI 项目和后端目录结构。
- 配置环境变量模板。
- 建立 Supabase 表结构 SQL。
- 打通本地前后端联调。

#### 阶段 2：行情能力
- 接入 AkShare。
- 实现股票代码校验。
- 实现股票概览接口。
- 统一图表数据格式。
- 在前端渲染股票信息和 K 线图。

#### 阶段 3：AI 分析能力
- 定义 `AnalysisOutput` Pydantic 模型。
- 编写 DeepSeek Prompt。
- 实现分析接口。
- 增加结构化输出重试与错误处理。
- 在前端展示分析结果和保存状态。

#### 阶段 4：历史记录能力
- 建立分析记录入库逻辑。
- 实现历史列表接口和详情接口。
- 完成历史记录页筛选、分页和详情弹窗。

#### 阶段 5：质量收尾
- 补齐异常处理。
- 完成部署配置。
- 完成 README 和交付材料。
- 完成本地与线上验收。

### 4.3 任务拆分建议
- 前端任务
  - 路由与页面骨架
  - 表单交互与状态管理
  - 图表组件
  - 历史记录列表与详情弹窗
- 后端任务
  - 股票数据服务
  - AI 分析服务
  - Supabase 存储服务
  - 错误处理与响应模型
- 交付任务
  - SQL 脚本
  - 环境变量说明
  - Render 部署说明
  - Debug 记录

## 5. 开发规范

### 5.1 通用规范
- 统一使用 `TypeScript` 和 `Python 3.11+`。
- 命名必须语义化，避免 `data1`、`temp`、`test2` 这类占位命名。
- 代码注释只解释意图、边界和非显然逻辑，不写废话注释。
- 任何对外响应结构必须先定义类型或 schema。

### 5.2 前端规范
- 页面只保留两个首版路由：`/` 和 `/history`。
- 所有接口调用统一收敛到 `api client` 层，不在页面里散写 `fetch`。
- 图表只消费后端标准化后的数据，不在前端重复做均线计算。
- 状态管理优先使用 `TanStack Query + local state`，首版不引入全局状态库。
- 表单校验优先在前端拦截明显错误，例如非 6 位数字代码。
- UI 风格保持一致，卡片、按钮、输入框、提示文案统一。

### 5.3 后端规范
- 项目分层固定为 `routers`、`services`、`schemas`、`core`。
- 路由层不写复杂业务逻辑，只负责参数接收、调用服务、返回响应。
- AkShare 返回的原始数据必须在服务层清洗后再进入响应模型。
- 模型输出只允许通过 Pydantic 模型解析，不允许直接透传原始文本。
- 对外错误码应稳定、可识别，避免把底层异常原样抛给前端。

### 5.4 数据规范
- 股票代码统一为 6 位字符串。
- 市场固定为 `CN`。
- 日期统一使用 ISO 格式。
- 金额和数值字段统一在后端完成基础格式化与字段命名。
- JSON 字段结构一旦对外暴露，不随意改名。

### 5.5 Git 与提交规范
- 每完成一个可验证的小功能再提交，不要堆成一次大提交。
- 提交信息建议使用：
  - `feat: add stock overview api`
  - `feat: build history page`
  - `fix: handle invalid symbol error`
  - `docs: add deployment guide`
- 不提交密钥、真实 `.env`、数据库凭证。

### 5.6 测试与质量规范
- 每增加一个接口，至少验证成功路径和失败路径。
- 每增加一个页面，至少验证加载态、错误态、空态。
- LLM 输出必须验证枚举字段是否合法。
- 保存失败不能导致分析结果丢失。
- 构建通过是最低要求，不等于功能通过。

## 6. 验收标准

### 6.1 功能验收
- 用户输入合法 A 股代码后，可以成功加载股票概览。
- 页面可以显示 90 个交易日 K 线、MA5、MA10、MA20 和成交量。
- 点击 AI 分析后，可以得到严格结构化的分析结果。
- 分析结果至少包含：
  - `summary`
  - `sentiment`
  - `risk_level`
  - `key_drivers`
  - `risk_factors`
- 分析结果可以写入 Supabase，并在历史记录页查询到。
- 历史记录支持按股票代码、情绪、风险等级筛选。

### 6.2 数据与接口验收
- `GET /api/health` 返回稳定健康状态。
- `GET /api/stocks/{symbol}/overview` 返回统一结构，且图表数据长度正确。
- `POST /api/analyses` 在保存成功和保存失败两种情况下都返回可处理响应。
- `GET /api/analyses` 支持分页和筛选。
- `GET /api/analyses/{id}` 能返回完整详情。

### 6.3 异常处理验收
- 非法股票代码要返回清晰错误提示。
- AkShare 数据获取失败时，要有明确错误提示。
- 模型返回不合法结构时，要进行重试并返回统一错误码。
- Supabase 保存失败时，前端仍能展示分析结果，并提示“未保存”。

### 6.4 UI 验收
- 页面在桌面端布局清晰。
- 页面在移动端不出现严重错位或横向滚动破坏。
- 加载中、成功、失败三类状态必须可见。
- 历史记录详情查看路径清晰，不需要猜测入口。

### 6.5 交付验收
- 仓库包含完整源码。
- 仓库包含数据库 SQL 初始化脚本。
- 仓库包含环境变量配置说明。
- README 包含本地启动方式、部署方式、在线地址、Prompt 说明、Debug 记录。
- 项目可以部署到 Render 并可公开访问。

## 8. 风险与应对

### 8.1 数据源风险
- 风险：AkShare 依赖外部数据源，偶发波动可能导致接口失败。
- 应对：后端包装统一异常，必要时限制返回“稍后重试”。

### 8.2 LLM 输出风险
- 风险：模型偶发不按 schema 返回。
- 应对：Pydantic 校验 + 自动重试 1 次 + 固定错误码返回。

### 8.3 部署风险
- 风险：前后端跨域、环境变量遗漏、Render 服务冷启动。
- 应对：提前配置 CORS、核对 `backend/.env`、先本地联调再上线。

### 8.4 时间风险
- 风险：48 小时内同时做功能、部署、文档，容易后期堆积。
- 应对：先做最小闭环，再做历史页和文档，不把部署拖到最后一小时。
